## 6a — fixes to extract first

The commit message of 0d11871b2 lists three bugs that apply without the monitor. Make each a
standalone patch on the current upstream driver, with `Fixes:` pointing at the commit that
added the MAX77705 charger driver, and `Cc: stable`:

1. status reports `POWER_SUPPLY_CHARGE_TYPE_NONE` (= "Charging") while CHG_EN is off; should be
   "Not charging" with an input, "Discharging" without.
2. the input current limit is written as `mA / 25` while it reads back as
   `(reg + 1) * 25 mA`; the vendor driver writes `mA / 25 - 1`.
3. `voltage_max_design` dereferences the battery info before it is read (only after the
   supply is registered); return `-ENODATA` until then.

Also from f38b6835f: the AICL handler underflow (`0 - 1` masked to 0x7F = 3.2 A) and its
unbounded loop are a real bug in the upstream driver if that handler exists there: a fourth
fix.

Patch 1 (MFD) cover note: it widens the accepted revisions on the strength of the vendor
driver's table; Lee may ask for a table instead of a special case. Ready otherwise.

## 6c — safety monitor (RFC)

Cover letter draft:

```
Subject: [RFC PATCH 0/4] power: supply: max77705: Battery safety monitor

On the Samsung Galaxy Tab S7+ the battery thermistor is read by a PMIC
ADC, not by the MAX77705, and the vendor driver monitors it in
software. The upstream driver enables charging at probe with the
watchdog off and no temperature check, which leaves charging unchecked
on such boards.

This RFC adds an optional monitor, enabled when the charger node has a
"battery-temp" IIO channel: charging only inside the battery's
alert-celsius range (with hysteresis), current/voltage/input limits
from DT written and read back, an optional safety timer, the charger
watchdog kept on and kicked only from a verified state, and the
standard charge_control_{start,end}_threshold and charge_behaviour
properties.

Questions: is a periodic software monitor acceptable in this driver,
or should temperature handling move to the power-supply core / a
thermal zone? Is a capacity threshold implemented in the driver the
right use of charge_control_end_threshold?

<OWNER NAME>
```

Must fix before even an RFC:

1. **BC1.2 cable detection (patch 6) is not upstreamable**: it reads BC_STATUS of the USB-C
   block at I2C address 0x25 with raw SMBus transfers on an address no driver claims. Upstream
   needs a MAX77705 USB-C/MUIC driver (Type-C class or extcon) that owns that block and
   reports the cable type; the charger then reads it through the power-supply / extcon API.
   Until then, keep patch 6 local.
2. `power_supply_get_by_name("max170xx_battery")` (patch 5): use a phandle
   (`power-supplies` / `monitored-battery` + `power_supply_get_by_phandle`), not a name.
3. Binding (patch 3): justify each new property; `maxim,safety-timer-sec` is a vendor property
   (check whether a generic charger property exists); `input-current-limit-microamp` for the
   DCP case may want a generic name.
4. checkpatch items in patch 4; the 785-line patch is hard to review: split by feature
   (temperature gate, limit enforcement, watchdog, timer, charge_behaviour).
5. Keep the "no channel = unchanged behaviour" guarantee explicit and tested.
